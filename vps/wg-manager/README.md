# WireGuard Manager - VPS Setup

## One-time setup

1. SSH into your VPS:
```bash
ssh ubuntu@193.123.183.184
```

2. Copy the wg-manager files to the VPS:
```bash
scp -r ./vps/wg-manager/* ubuntu@193.123.183.184:~/wg-manager/
```

3. On the VPS, run the setup script:
```bash
cd ~/wg-manager
chmod +x setup.sh
./setup.sh
```

4. Copy the generated WG_MANAGER_SECRET and WG_MANAGER_URL to your Next.js .env.local

5. Update platform config via superadmin with your VPS WireGuard public key:
```bash
sudo wg show wg0 public-key
```

## config.json - the part that only exists on the VPS

`config.json` is generated by `setup.sh` from `config.json.template` and is
**not in the repo** (it holds the shared secret). Nothing in the deployment
runbook copies it, so changes made to it on the VPS exist in exactly one
place. If this box is ever rebuilt, it is recreated from the template - so
the template must stay correct.

Two fields matter beyond the secret:

- **`tunnelSubnet` / `reservedIps`** - the range peers are allocated from.
  This must not overlap any subnet another product on the same VPS uses:
  two tunnels in one subnet give a tenant's router duplicate routes and
  silently break both tunnels. See `docs/router-and-wireguard.md`, "The
  shared-subnet trap". Changing it here is only one of three places - the
  VPS interface's own address and `PlatformConfig.wireguard.tunnelSubnet`
  in Firestore must agree.
- **`wgInterface`** - **currently inert.** `app.py` hardcodes `"wg0"` in
  every `wg`/`wg-quick` call and never reads this key. Changing it does
  nothing. Left in place because the field is harmless and wiring it up is
  the obvious fix if a second interface is ever needed; just don't trust it
  until then.

## Checking service status

```bash
sudo systemctl status wg-manager
```

## Viewing logs

```bash
sudo journalctl -u wg-manager -f
```

## Restarting

```bash
sudo systemctl restart wg-manager
```
