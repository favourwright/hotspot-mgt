# Decisions & Gotchas - Quick Index

A scannable list of every non-obvious choice and every real gotcha across this project, each pointing at the doc with the full story. Use this to jump straight to the relevant detail rather than re-reading everything; it's intentionally terse.

**Every entry is a single line, so grep it rather than reading the whole file.**
It is roughly 12k tokens end to end and you almost never need all of it:

```bash
grep -n -i 'voucher\|renewal' docs/decisions-and-gotchas.md   # by keyword
grep -n '^## ' docs/decisions-and-gotchas.md                  # the five sections
```

The five sections, in order: **Architecture decisions**, **Real incidents and
the fixes they produced**, **Things you'll find in the code that look like bugs
but aren't**, **Dead code you'll encounter**, **Test fixtures worth knowing**.

Grep for the nouns in the area you are touching (`voucher`, `addon`, `cron`,
`claims`, `portal`, `router`, `email`, `tenant`). If you are starting work in an
area you have never touched and the greps come back thin, read the whole file
once - it is cheaper than the incident it prevents.

## Architecture decisions

- **Multi-tenancy is path-based (`/{tenantSlug}/...`), not subdomain-based.** Never weighed on paper against the alternative - just what was built from the first version. → `docs/architecture.md`
- **Zod schemas are the single source of truth** for both runtime validation and TypeScript types - never define a type separately from its schema. → `docs/data-model.md`
- **`tenantId` always comes from the verified auth token, never from the URL or request body** - with exactly one deliberate exception: `/api/payment/verify`, where the caller is a customer who has no `tenantId` of their own to verify against, so they're trusted to assert which tenant they're paying. → `docs/billing-and-payments.md`
- **`verifyOwner()` accepts both `"owner"` and `"superadmin"`** - the root of every "superadmin can view, but not act on, any tenant's data" behavior in the app. → `docs/auth-and-security.md`
- **Role and `tenantId` live in Firebase custom claims, not in a per-request Firestore read.** Reverses the earlier design; the trade is that a session cookie is a snapshot, so any flow changing a signed-in user's role must call `refreshSession()`. → `docs/auth-and-security.md`
- **Reads are tenant-scoped by an `x-tenant-slug` header; writes are not.** Lets a superadmin read any tenant's data through the API (matching what the page gate already allows) while every mutation stays owner-only. → `docs/auth-and-security.md`
- **This product owns `10.20.0.0/24` on the VPS tunnel, deliberately separate from the `10.10.10.0/24` other products use.** Not cosmetic - a shared subnet produces duplicate routes on tenant routers. → `docs/router-and-wireguard.md`
- **Server-side caching is in four distinct places with different lifetimes**: tenant-by-slug (60s, tag-invalidated on edit), dashboard stats (60s, page-level only), per-tenant earnings (60s, one entry for the whole superadmin billing table), router config (5min, in-process `Map` rather than Next's cache because it holds credentials that must not be written to `.next/cache`). → `docs/architecture.md`
- **A payment that already succeeded is never undone by a later technical failure.** Shows up twice: a MikroTik hotspot-user-creation failure still keeps the payment and voucher (just marks it `"failed"` for retry), and a Paystack subaccount mismatch is logged, never used to block the payment. → `docs/data-model.md`, `docs/billing-and-payments.md`
- **`BillingPlan` pricing is snapshotted onto a `Tenant` at signup; `BillingPlan` limits are read live.** Deliberate asymmetry - price changes shouldn't retroactively apply to existing tenants, but entitlements should always reflect the plan's current real definition. → `docs/data-model.md`
- **Deleting a `BillingPlan` is smart, not absolute**: permanent if unused, archived (never hard-deleted) if any tenant still references it. → `docs/data-model.md`
- **Uninstalling the captive portal restores each hotspot profile to its *own* previous `html-directory`**, captured per-profile at install time - not a single value, and never our own directory. Storing one value flattened multi-profile routers onto the first profile's directory, which is how a tenant's custom login page got replaced with stock. → `docs/captive-portal.md`
- **A router backs exactly one location, enforced in the UI and API but not the schema.** Everything a location drives on the router - portal directory, profile list, user and session lists - is router-wide, so a second location would silently share and overwrite the first one's state. → `docs/locations-and-routers.md`
- **Legacy flat Firestore collections (`locations`, `plans`, `vouchers`, `payments`) are kept but dead** - nothing writes to them anymore; all real data is in tenant subcollections. A handful of orphaned hooks (below) still read from them, pointlessly. → `docs/data-model.md`
- **Addons are a fixed list in code (`lib/addon-catalog.ts`) with superadmin-editable pricing, deliberately not full CRUD** - unlike `BillingPlan`, which is pure configuration. An addon only does anything because a route calls `requireAddon` with its key, so one created from a UI under a key no gate references would be listed, sellable and chargeable while enforcing nothing. `BillingPlanFeatures.customBranding` / `apiAccess` / `prioritySupport` are already in exactly that state: editable in the dialog, checked in zero places. → `docs/addons.md`
- **The scheduled jobs run from an external cron-job.org account, not from the systemd units in `deploy/`** - those exist as a fallback and a record of the intended schedule, and are not installed on the VPS. Nothing in the codebase can see that account, so "did this job run" is answered from nginx's access log, never from `systemctl`. → `docs/cron-jobs.md`
- **A cron job that fails returns 200 and alerts nobody.** Partial failure is tolerated by design so one unreachable router cannot stop the other tenants, but the consequence is that `ok: false` goes only to the journal. → `docs/cron-jobs.md`
- **`alogin.html` and `status.html` are rendered by the router; `login.html` is rendered by us.** Only the login page needs our origin, because only it takes payment - and our origin being HTTPS against a plain-HTTP LAN hotspot is exactly what broke the login form once. → `docs/captive-portal.md`
- **No logout page is installed and the status page has no disconnect button** - sessions end on the keepalive timeout, not at the customer's choice. → `docs/captive-portal.md`
- **An owner can only mute emails flagged `optional` in the catalog, and the check lives in `sendEmail()` rather than at the call sites.** Operational, financial and account emails have no switch on purpose - muting "your router is offline" means opting out of finding out the business stopped working. Centralising the check means a new email cannot ship with a switch that silently does nothing. → `docs/emails.md`
- **Notification preferences are stored as a list of muted keys, not a map of every key to a boolean.** An absent entry means send, so a new email defaults to on for existing tenants with no migration, and a corrupt field or a failed read degrades into too much mail rather than silence. → `docs/emails.md`
- **We install our own `errors.txt` so RouterOS reports failures as stable tokens instead of English prose.** Matching the stock wording means matching sentences with usernames in the middle, in text that varies by version and that a tenant can edit. Stock patterns stay as a fallback for portals installed before this. → `docs/captive-portal.md`
- **Portal errors render as an inline alert, never a toast.** A toast fades, cannot be returned to, and sits away from the fields it concerns - exactly wrong for a blocking form error on a phone. → `docs/captive-portal.md`
- **Email verification deliberately blocks nothing - not a purchase, not onboarding - and the notice only appears once someone is signed in.** A customer registers from behind the captive portal's paywall, where no webmail is in the walled garden and their inbox is simply unreachable, so any gate on reading an email would end the purchase rather than improve the data. It is a data-quality control, not a security one. → `docs/auth-and-security.md`
- **Email OTP was considered and rejected.** Firebase has no email OTP, so it meant a custom build with its own rate-limiting and brute-force surface, bought to gain an experience advantage that only pays off in the one place verification cannot happen at all. → `docs/auth-and-security.md`
- **Changing an email never requires control of the old mailbox** - the confirmation goes to the new address and the old one is only notified. Not controlling the old address is the commonest reason to want the change, so confirming on it would trap exactly the people it should help. → `docs/auth-and-security.md`
- **Re-auth for an email change is enforced server-side on `auth_time`, not by the password dialog.** We mint the link with the Admin SDK so the email can be branded, and the Admin SDK does not enforce `requires-recent-login` the way the client SDK does. `auth_time` does not move on a token refresh, so only a real re-authentication satisfies it. → `docs/auth-and-security.md`
- **The custom action handler lives on the apex and must stay there**, because Firebase's authorized-domain list takes no wildcards and a per-tenant subdomain could never be listed. → `docs/auth-and-security.md`
- **Buying the same plan again before it expires extends the credential instead of issuing a second one.** Expiry is wall-clock from first login, so a customer renewing early genuinely has unused days left and a fresh voucher throws them away. A *different* plan always mints fresh, and that is the router's doing rather than a preference: a RouterOS user has exactly one profile and the profile carries speed, duration and the cap. → `docs/billing-and-payments.md`
- **The checkout asks who a repeat purchase is for, because no amount of history can tell.** A customer bought the same daily plan three times in nineteen minutes meaning to hand two codes to friends; all three stacked onto his own login. The answer rides on the Paystack charge's metadata, not the verify request, so the webhook and the reconciliation cron reach the same decision the browser would have. → `docs/billing-and-payments.md`
- **`intent: "fresh"` ignores the buyer's saved profile login too, not just their running plan.** A code meant for somebody else must not carry the buyer's own username. → `lib/voucher-renewal.ts`
- **Whether a renewal adds to what the customer had left or starts it again is the tenant's setting, not the code's.** `Tenant.renewalExpiryMode` and `renewalDataMode`, both defaulting to the original add-on-top behaviour, both tenant-wide, both on the plans page. A reset expiry is `now + duration` stamped immediately, never a return to the unactivated marker - that would write a null expiry onto a running voucher, which is the shape `resolveVoucherAction` reads as "never used". → `docs/billing-and-payments.md`
- **A reset data allowance is a cap *and* a counter reset, and the second half is the one that must not be skipped.** RouterOS measures lifetime counters against `limit-bytes-total`, so handing a customer the plan's allowance without clearing what they already spent reads as already exhausted on a plan they just paid for. The retry path reads the mode off `Voucher.renewal` so a retried renewal clears them too. → `lib/voucher-fulfilment.ts`
- **A reset renewal can move a customer's expiry backwards, and the checkout says so before they pay.** Renewing a Daily while a Weekly is running ends the credential tomorrow. The dialog is given both dates precisely so the loss is in words rather than inferable from a date. → `components/shared/purchase-intent-choice.tsx`
- **`Voucher.renewal` is the only record of what a renewal discarded.** The chain (`renewalOf`/`supersededBy`) says a renewal happened; under either reset mode the expiry, the cap and the byte counters it replaced are overwritten on the router within the same second. The modes are copied onto the voucher rather than read back off the tenant, so flipping a setting later does not revise history. → `docs/data-model.md`
- **The hotspot-user detail dialog showed a renewed login's first purchase, and with it the wrong payment.** `vouchers.find(v => v.username === username)` over an unordered query returns whichever document Firestore hands back first, which in practice was the original - so an owner on a support call read out a reference for a charge that was not the one in question. Use `liveVoucherFor`, and the dialog now lists the whole chain rather than replacing one truth with another. → `lib/hotspot-user-detail.ts`
- **A renewal re-applies the plan's MikroTik profile and inherits the previous voucher's `deviceMac`.** Without the first, a tenant who edited the plan's profile has new voucher documents claiming a speed and duration the router is not enforcing. Without the second, a renewal bought from the storefront makes the newest voucher for that code one with no device, losing `lastVoucherForDevice` and the portal's "welcome back" card. → `lib/voucher-fulfilment.ts`
- **A renewal still writes its own voucher document, and the one it replaced becomes `"superseded"`.** Revenue sums `payments`, but the voucher counts are live `count()` queries, so a renewal that wrote nothing would under-count sales forever. A distinct status rather than an early `"expired"`, because two crons key off `"active"` and both would otherwise act on a date that no longer applies. → `docs/data-model.md`
- **A customer who picks their own wifi username does not get the name they typed** - they get `<handle>-<suffix>`, with a suffix generated once per customer. Not cosmetic: it makes every handle always available, so there is no "is this taken" oracle against a hotspot login that has no rate limiting and no lockout. → `lib/voucher-credentials.ts`
- **Chosen voucher credentials live in their own subcollection, not on the `TenantCustomer` document.** That document is created by a purchase and is what `maxCustomers` counts - writing one for somebody who has only opened their profile page would spend a seat the tenant pays for. Per tenant rather than per account for a second reason: an owner can read their own vouchers' passwords, and must not thereby learn the one a customer uses elsewhere. → `docs/data-model.md`
- **`voucher-reap` is driven from voucher documents, never from the router's user list.** A router user with no voucher behind it is the tenant's own, made by hand in Winbox, and an automated delete that guessed wrong there would be unrecoverable. → `docs/cron-jobs.md`
- **The password-reset email stays on Firebase's sender on purpose.** `sendEmail()` treats an unconfigured Mailtrap template as a silent skip, which is correct for a notification and unacceptable for account recovery. → `docs/emails.md`

## Real incidents and the fixes they produced

- **No server-side auth existed at all, originally** (`proxy.ts`'s middleware explicitly deferred everything to client-side layout checks, by original design). This meant admin/superadmin pages fetched and served real tenant data regardless of who was asking. Fixed by adding an entire session-cookie + server-side verification layer that didn't exist before. → `docs/auth-and-security.md`
- **The visible "flash" of protected content before redirect** was a separate, smaller bug on top of the above: two layouts checked `loading` before rendering but never checked the actual auth *result* - present since the very first implementation of the tenant-admin layout, not a regression. → `docs/auth-and-security.md`
- **A brand-new superadmin registration could get silently stuck as `"customer"`** forever, due to a timing race between Firebase Auth's token listener and this app's own Firestore user-doc creation - made worse once by a long-running dev server holding a stale `SUPERADMIN_EMAIL` env value. Fixed both the race (force a token refresh after registration) and the underlying fragility (the register route now self-heals the role on every call, not just the first). → `docs/auth-and-security.md`
- **RouterOS silently loses variable scope** when a multi-line script is pasted into an interactive terminal unbracketed - each `:local` line executes as its own separate command. Fix: wrap the whole script in one outer `{ }` block. → `docs/router-and-wireguard.md`
- **A WireGuard tunnel can fully, successfully handshake and still be completely unreachable** - ping and handshake state are different signals, and conflating them (as the original reachability check did) makes two unrelated failure causes look identical. → `docs/router-and-wireguard.md`
- **The daily Firestore read quota was exhausted in ordinary solo testing**, taking the whole app down with `8 RESOURCE_EXHAUSTED`. The database held ~23 documents - the cause was never data volume but *how often* unbounded queries ran: dashboards computed "all-time revenue" by downloading every payment, list pages fetched whole collections then `.slice(0, 10)`, and every authenticated request re-read the user document. Fixed with `count()`/`sum()` aggregations, `limit()` pushed into the queries, custom claims, and the caching layers above. → `docs/architecture.md`, `docs/auth-and-security.md`
- **Two WireGuard tunnels in the same subnet silently broke both of them** - including an unrelated product's. Handshakes stayed healthy and no traffic passed, and it was initially misread as "the router won't reconnect after a power cut" because the ECMP hash reshuffles on reboot. → `docs/router-and-wireguard.md`
- **Local sign-in broke completely because `.env.local` held the *production* `NEXT_PUBLIC_APP_URL`**, with the localhost one commented out above it to be toggled by hand. Nothing errored server-side: the session cookie simply went out with `Domain=ogawifi.online`, the browser rejected it as an invalid domain for `localhost`, every subsequent render saw no session, and sign-in bounced back to `/auth?redirect=...` instantly. The only visible symptom was two `Cookie "session" has been rejected for invalid domain` lines in the browser console, which look like a cookie bug rather than a config one. Fixed by splitting env into two local files Next.js chooses between on its own - `.env.development.local` (test values, read by `npm run dev`) and `.env.production` (live values, read by `npm run build`) - and deleting `.env.local` entirely. `.env.local` is the trap: it is loaded in *every* environment and outranks `.env.production`, so recreating one silently builds production from test values. `npm run env:check` fails if one appears. → `docs/deployment.md`
- **Building on the production VPS directly caused a real outage** - 956MB RAM, no swap at the time, `next build` hung and eventually made the whole VPS unresponsive, requiring a hard reboot. Deployment strategy permanently changed to "build locally, rsync only the output" as a direct result. → `docs/deployment.md`
- **A TanStack Query mutation's `invalidateQueries` is a silent no-op if nothing actually subscribes to that query key.** Several admin tables defined the invalidation but rendered straight off server-passed props instead of `useQuery` - meaning a create/edit/delete appeared to "work" (the mutation succeeded) but the visible list never updated without a manual page reload. Not a crash, not an error - just quietly stale data. Fixed across every affected table by actually subscribing via `useQuery(initialData: ...)`. → `docs/architecture.md`
- **The sidebar's active-link highlighting used `pathname.startsWith(href)`**, which also matches any sibling route that happens to share the same prefix (`/superadmin/billing` matching `/superadmin/billing-plans`). Fixed to require a full path-segment boundary. Same latent bug existed in two separate sidebar components.
- **`@google-cloud/firestore` is an *optional* peer dependency of `firebase-admin`** and can silently fail to install, causing every Admin-SDK-dependent API route to fail with an opaque empty 500 - pin it as an explicit direct dependency in `package.json`, don't rely on it coming along for free. → `docs/deployment.md`
- **Adding a dependency almost never means installing it on the VPS.** The deploy ships `.next/`, and the App Router bundles dependencies into it; `gsap`, `lenis` and three `@dicebear` packages all run in production while being absent from the box. Only Next's default-external list, `serverExternalPackages`, native modules, and the direct dependencies reachable through those have to be installed there - today that is `firebase-admin` and the entry above. The runbook said the opposite for a while. `npm run deps:check` answers it. → `docs/deploy-runbook.md`
- **`NEXT_PUBLIC_*` env vars are baked in at build time, not read at runtime** - a mismatch between what's in the repo's build environment and what the production server actually needs (a missing port number, a stale test-mode key) ships silently and only shows up as a runtime symptom in production. → `docs/deployment.md`
- **A Let's Encrypt wildcard certificate can only be issued over DNS-01**, which is why the DNS zone had to move to a provider with a free API (Cloudflare). A second, independent benefit decided the shape of the whole setup: DNS-01 never needs port 80, which on this VPS belongs to Apache and two unrelated live products. → `docs/domain-and-tls.md`
- **`certbot renew` does not reload nginx.** nginx reads the certificate once at start, so without a `renewal-hooks/deploy/` hook the certificate renews silently and the server keeps serving the old one until it expires - breaking every tenant subdomain at once, ~60 days after the renewal appeared to succeed. → `docs/domain-and-tls.md`
- **`http2 on;` is nginx 1.25+ syntax** and brings the entire config down on the 1.18 that ships with this VPS's Ubuntu - taking Apache's unrelated sites with it on reload. The 1.18 form is `listen 443 ssl http2;`. Always `nginx -t` before reloading on a shared box. → `docs/domain-and-tls.md`
- **Cloudflare's zone import silently misses records.** Moving the domain's DNS nearly dropped the `MX` and `autoconfig`/`autodiscover`/`email` records for the domain's email, which would have broken mail - invisibly, since the website would have been perfectly fine. Diff the registrar's record list against Cloudflare's after importing. → `docs/domain-and-tls.md`
- **Opening a port on an Oracle Cloud VPS takes two firewalls** - the VCN security list *and* the host's iptables, whose `INPUT` chain ends in `REJECT` so the rule must be inserted rather than appended, then `netfilter-persistent save`d or it vanishes on reboot. Missing either one produces a hang, not a refusal, which reads like a DNS or nginx fault. → `docs/domain-and-tls.md`
- **Changing the root domain is not just a DNS change** - every router that already has the captive portal installed carries a walled-garden allow-list naming the *old* domain, and keeps blocking the new one until the portal is reinstalled from the location's admin page. → `docs/domain-and-tls.md`, `docs/router-and-wireguard.md`
- **A domain-scoped session cookie does not make a user signed in on a subdomain.** Firebase's client-side auth persists per-origin (IndexedDB), so server components and the browser disagree about who is logged in the moment you leave the apex - showing up as a redirect to `/auth` and as `Authorization` headers with no token. Fixed with a session-cookie → custom-token exchange (`/api/auth/bootstrap`). → `docs/auth-and-security.md`
- **Signing out on one subdomain leaves every other origin believing it is still signed in, and that belief loops.** The cookie clears domain-wide; the apex's IndexedDB does not, because no page of ours ran there to clear it. `ogawifi.online/superadmin` then bounced to `/auth?redirect=/superadmin` on the server's answer and straight back on the browser's, forever. An expired or revoked cookie reaches the same state with nobody signing out of anything. Fixed by making the cookie the truth in *both* directions: `reconcileClientSession()` discards client state the server does not back, and `/auth` asks the server before it bounces anybody. `npm run test:session-reconcile`. → `docs/auth-and-security.md`
- **Signing out of Firebase without clearing the server session cookie became a "can't log out" bug** the moment that bootstrap existed: the listener fires with no user, the cookie is still there, and the client trades it straight back for a token. Clear the session *before* `signOut()`. → `docs/auth-and-security.md`
- **Serving a tenant at both `/{slug}/...` and `{slug}.domain/...` makes link generation undecidable** - the same relative path means a tenant page on one host and nothing on the other. Fixed by making the subdomain canonical with a 308 from the path form, so the prefix becomes a single build-time value (`lib/tenant-url.ts`) instead of something every link has to infer. → `docs/domain-and-tls.md`
- **`router.push()` to another origin does not reliably do a full page load**, so any navigation that crosses from one tenant's host to another (or from the apex to a tenant) has to go through `window.location` - which is what `pushTenantUrl()` exists to decide. → `docs/domain-and-tls.md`
- **An axios `baseURL` of `NEXT_PUBLIC_APP_URL` turns every admin API call into a cross-origin request** the moment tenants move to subdomains: `starlink.ogawifi.online` calling `ogawifi.online/api/...` triggers a CORS preflight nothing answers, so the request fails before it is sent. The base must be relative in the browser - `/api` is host-neutral in `proxy.ts` and answers on every host. → `docs/domain-and-tls.md`
- **Anything that derived the tenant slug from `window.location.pathname` silently stopped matching on a subdomain**, where an admin page is at `/admin/locations` rather than `/starlink/admin/locations`. The slug moved into the hostname. This one fails quietly: it only affects a superadmin viewing a tenant, whose requests then carry no `x-tenant-slug` at all. → `lib/app-host.ts`
- **Firebase Auth's authorized-domain list does not accept wildcards**, so a per-tenant subdomain scheme can never be fully listed. Survivable only because the list gates OAuth popup/redirect sign-in and email action links with a `continueUrl` - neither of which this app uses. Adding either means keeping that flow on the apex. → `docs/domain-and-tls.md`
- **An invalid DNS-provider API token breaks nothing visible until the certificate expires.** `certbot renew` fails silently against a revoked Cloudflare token for weeks; the running nginx keeps serving the still-valid cert, so the only signal is `certbot renew --dry-run`. Run it after any token change - that is what `npm run cloudflare:token` does automatically. → `docs/domain-and-tls.md`
- **A Cloudflare API token with a TTL is how renewal dies quietly.** Why the old token became invalid was never established - a lapsed TTL and a deleted token look identical from here, both reporting `9109`. Either way nothing warns, and certbot keeps failing against a certificate that is still valid. Create the replacement with no TTL, scoped to one zone with `DNS:Edit` + `Zone:Read` only, and no client-IP filter - `scripts/update-cloudflare-token.sh` verifies from your laptop but certbot uses it from the VPS, so an IP filter breaks one end or the other. → `docs/domain-and-tls.md`
- **The domain served Apache's directory index on port 80 for months.** The `A` records point at a box whose port 80 belongs to unrelated products, so `http://ogawifi.online` listed `/var/www/html`. Fixed additively with a name-matched vhost that 301s to HTTPS and 403s the domain on 8081/8082, modifying none of the three existing vhosts. **Its filename must sort last in `sites-enabled`** - Apache's default vhost per port is the first one parsed, so a file sorting earlier becomes the default and captures IP traffic, which is how the legacy products are actually reached. It is hostname dissociation, not access control. → `docs/domain-and-tls.md`
- **HSTS applies to a hostname on every port, not just 443.** Once set on `ogawifi.online`, a browser refuses `http://ogawifi.online:8081` outright rather than reaching whatever is there. Harmless here because the legacy products are reached by IP and HSTS never covers bare IPs - but it is the reason to check what else answers on a hostname before enabling it. The header was also deliberately withheld until `certbot renew --dry-run` passed, since with `includeSubDomains` a certificate expiry stops being a clickable warning and becomes an unreachable site. → `docs/open-items.md`
- **A patched Ubuntu package still reports the upstream version, so banner scanners report it as vulnerable.** An NCSC/Netcraft notice flagged `ogawifi.online:8081` for the PHP2Shell RCEs (CVE-2026-109618/109619). The box was already fixed: Ubuntu backports into `8.1.2-1ubuntu2.28` without bumping the version string Apache advertises. Check `zcat /usr/share/doc/php8.1-common/changelog.Debian.gz` for the CVE and confirm Apache restarted *after* the module's mtime - with `mod_php` the patch does nothing until it does. Note the app itself contains no PHP; `:8081` is `globlinksadmin`. → `docs/domain-and-tls.md`
- **Deleting a voucher document to clear reconciliation drift would quietly rewrite history.** Revenue is safe (it sums `payments`), but `totalVouchers`/`activeVouchers`/`failedVouchers` and superadmin's `totalVouchersAllTenants` are live `count()` queries over the vouchers collection, the matching payment stores the `voucherId`, and `firestore.rules` lets the customer read their own copy. Drift is cleared by deleting on the *router* or by a reversible `archivedAt` flag instead - never by removing the document. → `lib/hotspot-users.ts`
- **Locking down the claim path locked the superadmin out instead.** The fix below added a check that `/api/auth/register` could only mint `superadmin` for the address in `SUPERADMIN_EMAIL` - correct - but when it could *not* confirm that, it resolved the role to `"customer"` and **synced that**. The VPS turned out to hold a stale `SUPERADMIN_EMAIL` naming an address with no account in the project, so the real superadmin was demoted to `customer` on every single sign-in and bounced straight out of `/superadmin` by `requireSuperAdmin`. Nothing was wrong with the account; a server-side env value had drifted years earlier and had been harmless until code started acting on it. Two lessons, both now pinned by `npm run test:register-claims`: **refusing to grant an unproven elevation is right, writing a demotion from the same signal is not** - the signal is our own configuration, not evidence about the account - and an unconfirmed claim must leave existing claims untouched and log loudly instead. A genuine demotion still comes from the document, which is the only place it should. → `docs/auth-and-security.md`
- **`npm run env:diff` compared names and not values, and that is how the drift above stayed invisible.** Both files had `SUPERADMIN_EMAIL`, so the diff was clean while the values had not matched for a long time. It now also reports names that are set on both sides with **different values**, as truncated hashes - never the values, which is what keeps it safe to run and to paste. A differing hash is a question rather than a verdict: some values are meant to differ between a developer box and production.
- **Any signed-in customer could make themselves superadmin, straight from the browser console** - the same hole as the tenants one below, on `/users/{uid}`, and it survived that fix. The rule was `allow update: if isOwner(userId)`, and `role`/`tenantId` on that document are not display fields: `/api/auth/register` runs on **every sign-in** and minted custom claims from them, after which every request trusts the claims with no Firestore read. So `updateDoc(doc(db,'users',uid), {role:'superadmin'})`, sign out, sign in, and the token is genuinely superadmin - or `{role:'owner', tenantId:'<someone else>'}` for their routers, plans and bank details. The same write also defeated the `isSuperAdmin()` helper in the rules, which reads that document. Closed the writes (nothing in the app has ever written client-side) and made the register route confirm what the document asks for: superadmin only for the `SUPERADMIN_EMAIL` address, an owner's `tenantId` checked against that tenant's `ownerUid` and only when the claim actually changes, so an ordinary sign-in still costs no extra read. → `docs/auth-and-security.md`
- **A tenant owner could grant themselves anything, straight from the browser console.** `/tenants/{tenantId}` was `allow update: if isSuperAdminOrOwner(tenantId)` with no field restrictions, so one `updateDoc` could zero `platformFeePercent`, clear `monthlyFee`, flip `subscriptionStatus` to `"active"`, or change `planId`. The same document was world-readable while holding bank details and Paystack codes. Found while designing addons, because an entitlement stored there would have been self-grantable. Nothing in the app ever wrote client-side, so closing it broke nothing. → `docs/auth-and-security.md`
- **Pricing the captive-portal addon took a live venue's wifi offline.** `getEntitlementState` fails closed, correctly, so the moment the addon went from free to ₦20,000 the tenant who already had a portal installed started serving "Sign-in is unavailable" to their customers, who could no longer buy vouchers. Nothing was broken; the grandfathering step was simply skipped. **Adding a gate to a feature people already use takes it away from them the moment you price it** - run `npm run addons:seed -- --grandfather` first, always. → `docs/addons.md`
- **One Paystack customer code is shared by a tenant's platform subscription and every addon subscription they buy.** The webhook resolved subscription events by customer code alone, which with addons meant an addon's `subscription.create` would overwrite `tenant.paystackSubscriptionCode` and silently sever platform billing from its real subscription, an addon's failed invoice would mark the whole tenant `past_due`, and an addon renewal would email "your subscription renewed". Fixed by routing on `subscription_code` through `subscriptionIndex`, with `plan_code` attribution for the one event that populates it. → `docs/addons.md`
- **The captive portal used to sell to anonymous guests**, keyed to the device MAC, because signing up was assumed impossible behind a paywall. It was not: registration here is email and password only, with no verification email and no OAuth popup, and `*.googleapis.com` is already in the walled garden. Purchases now require an account everywhere. Zero guest purchases were ever recorded, so nothing historical depended on it. The one real trap during removal: `/api/payment/verify` returned voucher credentials when `purchaser.isGuest`, and that flag is always false now - the condition had to move to "was this bought from the portal" (`deviceMac` present) or the portal would have silently stopped showing credentials and auto-login would have broken. → `docs/captive-portal.md`
- **A voucher could be minted for the wrong person from a genuine reference.** `/api/payment/verify` checked that the charge succeeded, that the amount matched the plan and that the plan, location and router were live - everything except whether the signed-in caller was the person who paid. Both checkout paths already stamp `userId` into the Paystack metadata for the webhook's benefit, so the transaction says who bought it; fulfilment now refuses when that disagrees with the caller, with the same message a bad reference gets. Only enforced when the metadata carries a uid, so a charge recovered by the reconciliation job from Paystack's own records is unaffected. → `docs/billing-and-payments.md`
- **A customer paid and got nothing, and nobody found out for a day.** Voucher fulfilment ran only inside `/api/payment/verify`, called by the buyer's browser after the Paystack popup. On a captive portal that is the weakest possible place for it: the buyer is behind the paywall and the bank's 3DS step navigates the page away. When the call never landed there was no payment record, no voucher, no email and no alert - the only trace was Paystack's receipt to the customer. A reconciliation of Paystack against Firestore found 5 successful charges and 1 on record. Fixed by extracting fulfilment into `lib/voucher-fulfilment.ts` and driving it from three places: the browser, the `charge.success` webhook, and a 15-minute reconciliation cron. → `docs/billing-and-payments.md`
- **`charge.success` could mark a tenant's platform subscription paid when they bought a voucher from their own portal.** The handler resolved the charge by customer code, and a tenant using the email on their platform subscription would match themselves. Fixed by checking voucher metadata first, so a sale is identified as a sale before anything tries to infer a tenant from the payer. → `docs/addons.md`
- **Nothing in the codebase ever wrote `status: "expired"` to a voucher.** The crons synced the expiry *date* and never the *status*, so every voucher stayed `"active"` forever and `/admin/users` grew a permanent "the platform and the router disagree about them" warning, one per plan that had ever run out - a drift report that could never be cleared by any amount of syncing. `voucher-expiry` now closes them out against **our** `expiresAt` rather than the router's verdict, so it still holds when the router is unreachable. → `docs/cron-jobs.md`
- **A backtick anywhere in the generated portal CSS or script, including inside a comment, ends the TypeScript template literal.** It fails at build time, but the reported line is nowhere near the cause - this cost a real session over the word "quota" in a JSDoc comment. Same file: a literal `$(` is eaten by RouterOS before the browser sees it. → `docs/captive-portal.md`
- **A usage bar built from the router's session `limit-bytes-total` reads 0% used forever**, because that value is the *remaining* allowance and resets on every login. The quota travels in `plan.json` instead. The matching bug underneath it: `createHotspotUser` never wrote `limit-bytes-total` at all, so a data limit shown everywhere in the UI was enforced nowhere. → `docs/captive-portal.md`
- **RouterOS does not fold a session into `/ip/hotspot/user`'s byte counters until that session ends**, so every surface that summed those counters alone showed a connected customer 0 B used for the whole of their first session - the admin dialog, and the customer's own voucher page next to a live "Connected" badge. Measured on a live router on 2026-10-19: over 10 minutes across 28 concurrent sessions, all 56 user-counter readings moved by 0 while 51 of the 56 session counters moved, one by 132MB. Usage is now `lifetime counters + every open session`, in `totalBytesUsed`. The trap next to it: the session's own `limit-bytes-total` reads like a live remaining-allowance and is not one over REST - it is a login-time snapshot holding to `user limit - (user bytes-in + bytes-out)` exactly, with zero drift on all 28, so `quota - it` just returns the frozen counters by a longer route. `remain-bytes-total`, which the router-rendered status page uses correctly, is a page-render variable and absent from the REST fields. → `docs/captive-portal.md`
- **One hotspot username can hold several concurrent sessions**, on any profile with `shared-users` above 1, and a production router was carrying two for one user. `findActiveSessionForUser` took `data[0]`, so usage undercounted by whatever the other devices had moved - the larger half, in the observed case. It is `findActiveSessionsForUser` and returns all of them. → `docs/captive-portal.md`
- **The captive portal fetched Paystack's `inline.js` on every visit, for every device that joined the wifi.** `PortalCheckoutDialog` was a static import rendered unconditionally with `open={false}`, so its body ran on mount and `usePaystackInline`'s effect fired - a third-party script on the critical path of a page whose whole audience has not paid for internet yet. It is `next/dynamic` and mounted only once opened, and the plan list moved off the portal to `/{slug}/portal/plans` entirely. This was the "the portal is slow" complaint. → `docs/captive-portal.md`
- **Any link between the two portal routes must carry the router's session query string**, which only ever reaches the first page the router redirects to. Losing `link-login-only` means a paid-for voucher cannot be handed to the router; losing `mac` means no `deviceMac`, which is what `/api/payment/verify` keys on to return the credentials. Both fail silently, after the money has moved. Use `portalHref`, never a hand-built URL. `error` is deliberately dropped instead, so a stale failure is not re-raised after a navigation. → `docs/captive-portal.md`
- **The portal's WhatsApp link uses the `whatsapp://` scheme, never `wa.me`.** `wa.me` is an HTTPS host that is not in the walled garden, so tapping it from behind the paywall does nothing at all. The scheme opens the app with no network. The message still cannot send until the customer has data, and fixing *that* means whitelisting WhatsApp for every unauthenticated client on the network - a tenant's decision, not a default. → `lib/phone.ts`
- **The private-MAC notice tenants brought from their old portals was wrong, and shipping its wording would have cost support calls.** "May stop you from logging in" does not hold here: sign-in is a username and password posted to the router and a rotating address does not block it. What it really breaks is `lastVoucherForDevice` recognising a returning device and a plan's `sharedUsers` count. The copy is ours and fixed, and on by default (a schema default, so a tenant who switches it off keeps it off). → `docs/captive-portal.md`
- **A string replacement that silently doesn't match ships a half-edited page.** A brand-header change applied to `alogin.html` and not `status.html`, deployed, and was caught only by looking at a screenshot. Assert every replacement in a generated file. → `docs/captive-portal.md`
- **One `disabled` flag keyed off "is anything loading" greys out an entire list.** Every plan's button read "Checking..." when one was pressed, because the state was a single `checkingPlanId` compared with `!== null` instead of `=== plan.id`. Took two attempts to fix: the first changed only the label and left the disabling wrong. → `components/tenant/customer-home.tsx`
- **`error=$(error)` in the login shim is forwarded unescaped, and MikroTik offers no `-esc` variant for it.** A stock message containing `&` or `?` truncates the rest of the query string, taking `link-login-only` with it. The errors.txt we install sidesteps this by emitting only `[a-z-]` tokens; a router still on stock messages is still exposed to it. → `docs/captive-portal.md`
- **Pointing one Firebase email template at a custom action URL silently breaks every other flow that page does not handle.** Password reset was already in production using Firebase's own handler; a page that only knew `verifyEmail` would leave resets landing somewhere that shrugged, with the email still sending and the link still valid. The handler covers `verifyEmail`, `verifyAndChangeEmail`, `recoverEmail` and `resetPassword`, and the console setting must be flipped only after the page is deployed. → `docs/auth-and-security.md`
- **A shared account card rendered the *viewer's* identity on someone else's settings page.** `AccountEmailCard` read the signed-in user, so a superadmin opening any tenant's settings saw their own address with working Change and Send buttons - inviting them to "fix" a tenant's email and silently change their own. Nothing could be written to the tenant (the API refuses a superadmin on writes), which is exactly why it was invisible. Any component keyed to "the current user" that renders inside a page about *somebody else* needs the subject passed in explicitly. → `docs/auth-and-security.md`
- **Customer-side pages carry their own `AppShell` and nav; the tenant layout only handles the suspended case.** A page that renders bare `PageContent` gets no navigation at all and looks nothing like the rest of the app. Both the first `/profile` page and the verification notice on `/my-vouchers` shipped that way. → `components/tenant/vouchers-client.tsx` is the shape to copy
- **The onboarding wizard persists to localStorage, and that blob holds bank details.** `onboarding-store` keeps bank code, account number and account name so the wizard survives a refresh. It is cleared the moment the tenant is confirmed on the complete page - previously only when someone pressed "Go to dashboard", so closing the tab left somebody's banking details on the machine indefinitely. `reset()` also calls `persist.clearStorage()`, because `set(initialState)` alone leaves the key behind as an empty husk. An *abandoned* signup still leaves them until that browser finishes or restarts onboarding. → `stores/onboarding-store.ts`

## Things you'll find in the code that look like bugs but aren't

- **An addon entitlement that is `past_due` with no `pastDueSince` stays entitled**, and an `active` subscription past its `currentPeriodEnd` still lapses. Both deliberate: the timestamp is ours to write so its absence means our data is wrong (denying a paying tenant over our own missing field is the worse failure), while trusting `active` alone would turn a webhook we never received into permanent free access. `npm run test:entitlements` pins both. → `docs/addons.md`
- **The portal directory is created empty, despite a code comment that used to say RouterOS populates it with stock copies.** Only the files we write are in there, which is why a page we do not generate falls back to RouterOS's built-in default rather than one on disk. → `docs/captive-portal.md`
- **`Voucher.userEmail` and `Payment.userEmail` keep the old address after an email change.** They record who bought what, at the address they bought it under; rewriting them would revise history and leave a receipt that no longer matches Paystack's. Only `users`, `tenants.ownerEmail` and the per-tenant customer records follow a change. → `docs/auth-and-security.md`
- **The login form now POSTs to `/api/auth/register` on every sign-in.** It creates nothing and sends no welcome mail on that path - it re-syncs custom claims and reconciles a changed email, which is what the route's own comments already claimed happened. → `docs/auth-and-security.md`
- **An expired voucher still enabled on the router is not drift for the first hour.** The platform closes a voucher out within minutes; the router clamps `limit-uptime` only on its next per-profile sweep, which is hourly for any plan of 12 hours or longer. Three daily-plan customers expiring within thirteen minutes of each other on 2026-10-15 were all reported as "the platform and the router disagree about them" for the next hour, with both sides healthy. The allowance now comes from the same function that set the scheduler's interval. → `docs/cron-jobs.md`
- **Renewal and data-cap arithmetic refuses to treat `0` as a number.** A RouterOS `limit-bytes-total` of `0`, empty or absent all mean no limit, and reading any of them as a quantity caps a customer at zero bytes - which reads as already exhausted, on a plan they just paid for. An uncapped user also never acquires a cap from a capped plan. `npm run test:voucher-renewal`. → `lib/voucher-renewal.ts`
- **A renewal writes its new expiry and byte cap to Firestore before it patches the router**, and sends absolute values rather than "what is there now, plus the plan". That is what makes the retry path idempotent instead of topping the customer up twice. → `docs/billing-and-payments.md`
- **A paid customer could be left with no voucher and nobody told, by a crash between two writes.** Fulfilment created the payment document, then talked to the router; a process that died in between left a payment with no voucher, and every later caller found the payment and reported "already done". Fixed with a server-only ledger (`fulfilments/{reference}`) written before the router is touched and carried out by `lib/fulfilment-runner.ts`, with the payment document now written last. The ledger, not the payment, is the race guard. → `docs/billing-and-payments.md`
- **Expired fulfilment ledgers are deleted by the `payment-reconcile` cron, not a Firestore TTL policy.** TTL policies need the Blaze plan and the project is on Spark (`gcloud` answers `billing disabled`). The field is still named `deleteAt`, so a real policy later is a console setting plus deleting `purgeExpiredLedgers`. → `docs/cron-jobs.md`
- **A renewal's RouterOS patch is stored in the ledger, not recomputed on resume.** It is derived from the router's expiry comment, and after the first attempt's patch lands that comment already holds the extended date: recomputing would extend it twice. → `lib/voucher-fulfilment.ts`
- **A charge that cleared and cannot be honoured becomes a `paymentReviews` record and an email, and the buyer is not shown the reason.** "Amount does not match" reads to a customer as "your payment failed", and the one thing they must not do is pay again. The reconcile cron skips a reference under review. → `docs/billing-and-payments.md`
- **An unused voucher blocks a repeat purchase only before Paystack opens, never during fulfilment.** Once money has moved, a payment that already succeeded is never undone - so an unused voucher that got past the pre-check simply produces a second one. → `docs/billing-and-payments.md`
- **`voucher-reap` keeps a cursor instead of filtering out what it has done.** A reaped voucher still matches "expired and old", and Firestore cannot match a field that older documents do not have, so a plain query would return the same finished rows forever and never reach new ones. → `docs/cron-jobs.md`
- **`uninstall-portal` is not gated behind the captive-portal addon** while `install-portal` is - on purpose, so a lapsed payment never traps a tenant's router in a state they cannot undo. → `docs/addons.md`
- **`"admin"` as a stored `role` value** - legacy, translated to `"owner"` on every read site, never migrated in Firestore. Deliberate "never touch old data" policy. → `docs/data-model.md`
- **A tenant's displayed price never changes even after a superadmin edits the plan they're on** - correct, not stale data. → `docs/data-model.md`
- **The expected tenant share must subtract Paystack's fee when the subaccount bears it.** A comped tenant on a plan with `paystackBearer: "subaccount"` receives the charge minus Paystack's cut, which is the arrangement working. The old expectation was price minus the platform's percentage with no fee term, so it was wrong by the fee on every sale and fired a "split mismatch" alert each time. `expectedTenantShareKobo` now derives the figure from the same `computeCheckoutSplit` that sent the split. → `docs/billing-and-payments.md`
- **`transaction_charge` is only sent when fee-passthrough is on, and the fee part of it only when the platform bears Paystack's fee.** Sending it unconditionally would make `Tenant.platformFeePercent` authoritative over the subaccount's stored `percentage_charge`, which drifts from it by design - silently moving money for any tenant whose plan was edited after signup. And adding the fee when the *subaccount* bears it charges for the same fee twice, once from the customer and once out of the tenant's payout. Both live in `computeCheckoutSplit`, shared by the storefront and the portal so they cannot disagree. `npm run test:split`. → `docs/billing-and-payments.md`
- **Every displayed date is pinned to `Africa/Lagos`, because the VPS runs UTC and nobody reading the app does.** The same payment showed 10:00 on the server-rendered dashboard and 11:00 on the client-rendered transactions page - one timestamp, two answers, an hour apart. `formatDate`/`formatDay` in `lib/utils.ts` carry the zone, and `startOfTodayInDisplayZone` does the same for "today" so the day does not start at 01:00 Lagos time. `npm run test:day-boundary`.
- **`formatDate` used to render unrecognised input as the current time.** Its coercion handled only `Date` and Firestore `Timestamp` and fell back to `new Date()`, so a row fetched through an API route - where JSON has turned the date into an ISO string - rendered as "now". A whole table column of identical dates, with nothing saying they were invented. It parses strings and numbers now and returns "-" for anything it cannot read, because a visible gap beats a plausible wrong answer. `npm run test:format-date`.
- **A table that formats its own dates will disagree with the page around it.** Both voucher tables carried a local `toLocaleDateString` with no timezone, so the same voucher read an hour earlier there than on the dashboard beside it - the identical bug `formatDate`/`formatDay` in `lib/utils.ts` were written to end, reintroduced by copy-paste in two components that never imported them. Use the shared formatters; they carry `Africa/Lagos`.
- **An early `return` above a hook makes a component's hook count conditional.** `hotspot-users-client.tsx` returned its "no locations yet" empty state above a `useEffect` and a `useMemo`, which is the one thing React forbids outright. It never fired because `locations` is a server-rendered prop that cannot change within a mount - so it was a trap armed for whoever later made it change, not a live bug. It was invisible for a different reason too: `npm run lint` had been crashing before it reached a single rule (below). → `components/admin/hotspot-users-client.tsx`
- **`npm run lint` crashed on every file and nobody noticed.** `eslint-config-next` sets `settings.react.version: "detect"`, and the `eslint-plugin-react` nested under it implements detection with `context.getFilename()`, which ESLint 10 removed - so every file died with `contextOrFilename.getFilename is not a function` before any rule ran. Pinning `settings.react.version` in `eslint.config.mjs` short-circuits the detection entirely. It had been failing long enough to hide 70-odd real findings, including the conditional hooks above. A lint that errors is not a lint that passes.
- **A query that gains a `where` needs an index, and nothing in the build tells you.** Adding a filter to a query that already has an `orderBy` requires a composite index. `tsc` passes, `npm run build` passes, every test passes, and the query works against an empty collection - it fails only at runtime, in production, on the single page that runs it, with `9 FAILED_PRECONDITION`. It has shipped twice: `getMergedHotspotUsers` began reading plans by location and took `/admin/users` down completely, and the transactions page's **email** lookup had never once worked in production, because the reference lookup beside it needs no composite index and that is what people paste. `npm run check:indexes` runs every shape the app uses against the live project and names the call site of any that has no index. Run it after touching a query. → `AGENTS.md` step 5
- **Paginated lists have one reference implementation, and two traps that have already bitten.** `lib/transactions.ts` is the shape to copy: server renders page one plus aggregated totals, everything after goes through an API route, filters reset paging, totals come from `count()`/`sum()` rather than the rows on screen, and free-text search becomes an exact lookup because Firestore cannot do substrings. The traps: order by `createdAt` **and** `__name__` or tied timestamps repeat or skip rows, and split the cursor on the **first** underscore because payment ids are `hs_<millis>_<random>` - splitting from the right yields `NaN`, silently drops the cursor, and "Next" returns page one for ever. Walk every page in a script against a raw collection read; it is the only thing that proves paging works. → `docs/architecture.md`
- **A partial promo discount applies to the signup charge, not to a recurring rate, and leaves no subscription behind.** Paystack Inline either charges a Plan's amount and subscribes, or charges an arbitrary amount and does not, so a reduced first payment is a one-off and `subscriptionStatus` stays null until the tenant pays full price at the end of the window. A flat discount larger than the fee is a full waiver, never a refund. → `docs/billing-and-payments.md`
- **A waiver ending is announced by the `plan-fee-due` cron and nothing else, and it is now the warning before trading stops.** An unpaid plan fee used to gate nothing at all, permanently; it now starts a grace window (`PlatformConfig.planFeeGraceDays`, default 3 days) after which new voucher sales stop. The email is still the only signal before that happens, so a run that silently stops means a tenant finds out by a sale failing. The job is registered and running; `docs/cron-jobs.md` claimed it was not for months after it was scheduled, so check the access log rather than the doc. → `docs/cron-jobs.md`
- **The "sales paused" email is found by scanning tenants, not waivers, and the one-time stamp lives on the tenant.** The waiver loop only ever sees tenants who had a waiver, so a tenant who cancelled a subscription would have been locked in complete silence. The stamp is cleared by `invalidateBillingLock` on every unlock path, so a second lapse years later is announced again rather than swallowed by a stamp left from the first. → `notifyNewlyLockedTenants`, `docs/cron-jobs.md`
- **The email generator's dash guard only checked literal characters, so `&mdash;` shipped past it.** A house style enforced on the source and not the output is not enforced at all: the entity looks like markup in the generator and renders as an em dash in the inbox. It now checks both spellings. → `scripts/build-email-templates.mts`
- **An unpaid plan fee pauses new sales and owner writes, and is deliberately not `Tenant.status = "suspended"`.** That flag makes `requireTenantOwner` call `notFound()`, which would lock the owner out of the page where they could pay, and it blacks out the tenant's public pages, punishing their customers rather than them. The billing lock is derived at read time, leaves everything readable, exempts billing itself, and never touches vouchers already sold - those are hotspot users on the tenant's own router and keep working regardless. → `lib/billing-lock.ts`, `docs/billing-and-payments.md`
- **`past-due` can never lock, however old the debt looks.** Paystack is mid-retry on a card in that state and will usually resolve it on its own. Cutting the tenant off there would cost the payment and the business over our own impatience. Same reasoning that keeps `past-due` out of `payment-due` in the first place. → `lib/fee-waivers.ts`
- **The grace window counts from the *latest* thing that has already happened, not the earliest.** A tenant whose trial ended in March and who then paid for April is owing from the end of April. Taking the earliest candidate would lock them the instant that subscription lapsed, with no grace at all. → `resolvePaymentDueSince`, `npm run test:waivers`
- **Paying during a trial is a plain charge, never the Paystack Plan.** Opening the Plan subscribes immediately, which charges today and burns the free days the tenant is paying to keep. The prepay path charges a one-off for the first month *after* the waiver and creates the subscription server-side with a `start_date`. Its metadata (`plan_fee_prepay`) exists so the webhook stands back rather than applying its usual "paid now, due in thirty days". → `docs/billing-and-payments.md`
- **Sending a lapsed tenant back through `/onboarding` to re-pick a plan looks like free reuse and is a free-trial exploit.** `create-tenant` grants a waiver whenever the chosen plan has `trialDays`, with no check for prior waivers, so every lapse would mint another free month - and its bank step would re-create a Paystack subaccount the tenant already has. The plan *card* is reused; the flow is not. → `components/tenant/plan-change-dialog.tsx`
- **An owner changing their own plan updates the Paystack split; the superadmin doing it does not.** Not an inconsistency: the superadmin path is bulk work that must never silently move money for everyone on a tier, while this is one tenant who was shown the new rate before confirming. Leaving it behind would overcharge them on every voucher until somebody noticed. The split goes first, and the plan only changes if it succeeded. → `app/api/admin/billing/plan/route.ts`
- **A downgrade below current usage is permitted on an explicit tick, not refused.** The tenant who needs a cheaper plan is usually the one already over its limits. Refusing leaves them with "pay or leave", which loses the account rather than the difference between two tiers. Nothing is deleted either way - limits are enforced at creation, so existing routers keep serving and only the next one is blocked. → `lib/plan-change.ts`
- **Account-level notices have one region and one ordering, because they did not.** The email-verification notice was mounted in a layout and the plan-fee notice was dropped into a single page, so they appeared together on exactly one route and the fee notice vanished the moment the owner clicked anything - on a banner telling them they owed money. The admin layout is now a server component so the region can fetch. → `components/system/notice-stack.tsx`
- **Cancelling a subscription writes nothing to Firestore; the webhook owns that.** `DELETE /api/admin/billing/subscription` only calls Paystack. `platformCancelled()` in the `subscription.disable` handler already sets `subscriptionStatus` *and* sends `owner.subscription_cancelled`, so a second writer would mean drift or two cancellation emails. It also disables the tenant's own `paystackSubscriptionCode`, never anything resolved from the shared customer code - that would take their addons down with their plan. → `docs/billing-and-payments.md`
- **A fee waiver waives the plan fee and nothing else, and cannot stop a running Paystack subscription.** Waivers (`lib/fee-waivers.ts`) sit on top of the tenant's own plan and expire at read time, so a trial ends by itself with nothing to migrate. But the commission is Paystack's subaccount split, not something this app sends per charge, and recurring charges are driven by Paystack's own subscription object - so a tenant who should genuinely pay nothing needs a *plan change*, not a waiver. → `docs/billing-and-payments.md`
- **`Plan.sharedUsers` is a display-only mirror of the router profile's `shared-users`, and absent means unknown, not 1.** The router owns and enforces the device count; the plan copies it at save time so the storefront, portal and receipts can show it without a router round trip per page view. Plans saved before it was captured have null and render no chip at all - defaulting to "1 device" would promise a number nobody checked. An edit made while the router is unreachable keeps the stored value, because an empty profile list means "could not ask", not "no limit". → `docs/data-model.md`
- **`PlatformConfig.paystackBearer` has no UI to change it** and always runs at its default.
